# Custom node inheritance (Skeleton extends Enemy)

## Context

The user wants custom-node *inheritance* in Scala: a custom node `Enemy`, and a
second custom node `Skeleton` that **extends `Enemy`**, is registered with Godot
as its own node type, and adds a `String` property (`skeletonName`).

The good news from exploration: the binding's registration machinery is already
**parent-agnostic** — it derives the Godot parent from the Scala superclass and
passes it to Godot as a plain string. So custom→custom inheritance is *almost*
free. Concretely, today:

- The macro `Register.auto[T]` derives the parent from the first non-trait
  superclass and uses its simple name as `parentClassName`
  (`language-binding-scala/.../register/Register.scala:49-61`). For
  `Skeleton extends Enemy` this already yields `"Enemy"` — no macro change.
- Inherited virtual overrides are detected: `declaresOverride` walks the whole
  base-class chain up to `GodotScriptClass` (`Register.scala:77-80`), so an
  `_ready` defined on `Enemy` is reported for `Skeleton` too.
- `ExportType[String]` exists (`register/ExportType.scala:48`).
- Once `Skeleton` is registered with parent `"Enemy"`, Godot's ClassDB exposes
  `Enemy`'s properties/methods on `Skeleton` automatically — no re-registration.

The **one real gap** is registration order. Godot requires a parent extension
class to be registered *before* its child, but `RegistrationScan` emits classes
in alphabetical order (`harness-scala/project/RegistrationScan.scala:65`,
`sortBy((pkg, name))`). `Enemy` < `Skeleton` works by luck; any pair where the
child sorts first (e.g. child `"Apparition"` extends base `"Undead"`) would fail
with a parent-not-found error. We make ordering correct (parents first).

Decisions from the user: property is `skeletonName` (avoids colliding with the
built-in `Node.name`); deliver as a **harness example** plus the ordering fix.

## Changes

### 1. Topological registration order — `harness-scala/project/RegistrationScan.scala`

Today (line 59-65) the registerable classes are sorted only by `(pkg, name)`.
Add a "depth" key so a class is always emitted after its in-module ancestors.

- Add a helper alongside `reachesEngine`:
  ```scala
  // hops up the in-module parent chain until the parent is an engine class
  // (or unknown); engine-rooted classes get depth 0, their custom subclasses 1, …
  def depth(name: String, seen: Set[String]): Int =
    byName.get(name).flatMap(_.parent) match {
      case Some(p) if byName.contains(p) && !seen.contains(p) =>
        1 + depth(p, seen + name)
      case _ => 0
    }
  ```
- Change the sort to `.sortBy(c => (depth(c.name, Set(c.name)), c.pkg, c.name))`.
  Single inheritance ⇒ a depth-ascending order is a valid topological order;
  `(pkg, name)` stays as a deterministic tiebreaker.

This is the only binding/build change required.

### 2. Make `Enemy` an extendable base — `harness-scala/src/main/scala/game/Enemy.scala`

A `final case class` cannot be extended. Convert `Enemy` to an open class:

- Drop `final` and `case` (keep it a plain `class`). The `var`-param auto-export
  still applies to plain classes (the macro's `ctorParamFields`,
  `Register.scala:261-264`, and the scanner's `allParamsConstructible` both
  cover plain classes — the existing docstring even says "a `case class` (or
  plain class)").
- Keep its `@func remainingHealth`, `@signal died`, and `_ready` override so the
  example still shows those features being inherited.

### 3. Add `Skeleton` — `harness-scala/src/main/scala/game/Skeleton.scala` (new)

```scala
package game

import io.github.optical002.godot.GodotPrint
import io.github.optical002.godot.engine.Tscn
import io.github.optical002.godot.register.*

/** Custom node that extends another custom node (Enemy), adding its own
  * exported String property. Registered with Godot as parent "Enemy". */
class Skeleton(
  var skeletonName: String = "Bonechill",
  hp: Int = 10
) extends Enemy(hp, None, Tscn.unassigned[Player]) {

  override def _ready(): Unit = {
    super._ready()                        // inherited Enemy._ready still runs
    GodotPrint.print(s"Skeleton._ready (skeletonName=$skeletonName, hp=$hp)")
  }
}
```

Notes:
- Skeleton's own `var skeletonName` is the only property it registers; `hp`,
  `remainingHealth`, `died` are inherited from `Enemy` via ClassDB.
- The `extends Enemy(...)` clause forwards `Enemy`'s required ctor args with
  sensible literals (`None`, `Tscn.unassigned[Player]`). Confirm the exact
  unassigned/default helper names at implementation time against
  `register/DefaultValue.scala` / `engine/Tscn.scala`; adjust if the API differs.
- All of Skeleton's primary-ctor params are either `var` or have a default, so
  `RegistrationScan.allParamsConstructible` accepts it and the macro factory can
  build it argument-free.

`GeneratedRegistrations.scala` is regenerated by the scanner — `Register.auto`
calls for both `Enemy` and `Skeleton` appear automatically, now correctly
ordered (Enemy before Skeleton).

## Verification

Per CLAUDE.md, a clean compile is **not** proof — do a headless run.

1. Build the lib (atomically swaps the `.so`):
   `cd harness-scala && sbt build`
2. Run the Godot project headless and read the output:
   `cd godot && godot --headless --path . --quit-after 5`
   (or via `--script verify.gd` if that's the project's harness — check
   `godot/` for an existing verify script/scene and reuse it).
3. Confirm in the output:
   - No `Cannot get class 'Enemy'` / parent-not-found / registration-failure
     errors (this is what the ordering fix guards against).
   - A `Skeleton` instance constructs, its `_ready` fires, and the log shows
     both `Enemy._ready` (via `super`) and `Skeleton._ready (...)`.
   - From GDScript/verify: `Skeleton` exposes `skeleton_name` (its own) **and**
     the inherited `hp` property and `remaining_health()` method.
4. Optionally open in the editor to confirm `Skeleton` appears as a creatable
   node deriving from `Enemy`, with `skeleton_name` in the inspector.
